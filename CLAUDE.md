# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

AssetDB is a Splunk app (no Splunk Enterprise Security required) that merges asset records from multiple lookup files into a single KV store collection (`assetdb`). The repo root is the app directory itself (`$SPLUNK_HOME/etc/apps/assetdb`). Tests, packaging and deploy tooling are described in `docs/TESTING.md`; `make lint` runs shellcheck, ESLint (`eslint.config.js`, warnings allowed, errors fail) and ruff (`pyproject.toml`).

## Commands

- Build the front-end: `npm run build` (runs `scripts/build-minjs.sh`) — Babel-transpiles `appserver/static/js/src/*.js` (browser targets in `package.json` `browserslist`) and minifies each to `*.min.js` with terser. It builds in a temp directory and only replaces the outputs if every file built. Requires `npm ci` first.
- Edit only `appserver/static/js/src/*.js`. The `*.min.js` files are committed build output (what the dashboard actually loads) and must be rebuilt after source changes.
- Build the custom visualizations: `npm run build:viz` (esbuild, `viz/build.mjs`) turns `viz/<name>/src/visualization.js` into two committed builds: `appserver/static/visualizations/<name>/{visualization.js,config.json}` (Dashboard Studio, registered in `default/visualizations.conf`) and `appserver/static/js/classic/<name>.min.js` (the classic dashboards; `@splunk/dashboard-studio-extension` is aliased to `viz/shared/classic-host.mjs`, which talks to the page by postMessage). Edit only `viz/`. The Explorer and Coverage dashboards are generated by `python3 scripts/build-dashboards.py` into `default/data/ui/views/assetdb_explorer.xml` and `assetdb_coverage.xml` (committed; `scripts/check-viz.sh`, part of `make test`, fails if any of it is stale).
- Python/SPL changes need no build; reload the app in Splunk (`.../debug/refresh` or restart) to pick up `.conf` changes. `local/` is gitignored and holds runtime overrides written by the UI.

- `scripts/e2e.sh --flow` and `--visual` (Playwright, `npm i --no-save playwright`): the UI against a real Splunk; `--visual` sweeps every tab at three widths for cut-off tooltips, spilled text and overlapping controls. `node tests/e2e/screenshots.mjs` regenerates `docs/img/*.png` for the README.
- `node tests/e2e/viz.mjs` runs both Studio visualizations in a headless browser against a mock of the Studio extension API, `node tests/e2e/classic.mjs` the classic build in an iframe fed by postMessage (no Splunk for either; `tests/e2e/viz-harness.mjs`). `scripts/e2e.sh --explore` opens the real Explorer and Coverage dashboards in both themes (needs the app deployed). Playwright must match the cached browser; `npm install`/`npm ci` remove it.
- `make test` — pytest (`tests/python`, targets `bin/adbmerge_core.py`), `node --test` golden SPL tests (`tests/js`, `UPDATE_GOLDEN=1 npm test` to refresh `tests/fixtures/golden`), min.js freshness (`scripts/check-minjs.sh`), deploy mock test, shellcheck.
- `make package` -> `dist/assetdb-<version>.tar.gz`; `make inspect` (AppInspect, tags from `APPINSPECT_TAGS`, waivers in `.appinspect-waivers`); `make deploy` / `make reload` (SSH deploy to the dev server, config in gitignored `.env.local`, see `.env.example`); `make integration`; `make all` runs the pipeline (`scripts/test-all.sh --skip-deploy` for local only). Always run deploy/reload with `--dry-run` first.
- Merge logic lives in `bin/adbmerge_core.py` (pure, unit tested); `bin/adbmerge.py` is the thin splunklib wrapper. `makeMergeSearch()` is tested by evaluating the unmodified `assetdb.js` in a vm sandbox (`tests/js/load-generator.js`).

## Architecture

The pieces only make sense together:

1. **Generator** (`appserver/static/js/src/generator.js`): a pure AMD module (no DOM/REST) that turns the `assetdb.conf` field array into the merge search as typed `{kind, text}` lines (`buildSearchLines`), plus the read-only preview searches (`buildPreviewSearches`). **To change merge behaviour edit the generator**, never the saved search. Everything it emits is covered by golden files (`tests/fixtures/golden`) and by tests that run the generated SPL on a real Splunk (`tests/integration/sandbox.py`). Gotchas learned the hard way: fields that start with `_` are internal and vanish through `stats`; `mvappend` with one argument is an eval error (use `mvappendOf`); `outputlookup` with zero results empties a KV collection unless `override_if_empty=false`.
2. **Configure UI** (`default/data/ui/views/configure.xml` → `js/assetdb.min.js`, styles in `css/assetdb.css`): a Simple XML page that mounts a SPA into `#ab_config`. It renders inside a **Shadow DOM** (the stylesheet is linked into the shadow root, so Splunk's styles and ours never touch each other; Playwright pierces it, plain DOM queries do not). The page has a light and a dark theme (host `data-theme`, set from the user's Splunk theme; the page sits on Splunk's own background, #f2f4f5 or #171d21; `css/page.css`, loaded by the dashboards, makes Splunk's panel transparent) and opens on the Sources tab. Tabs: Sources, Fields, Pipeline (the preview, then the generated search as one document with a stage outline), Settings. The preview is `buildPreviewDiff` (the merge minus every write, compared with `assetdb`) run as a job plus a cheap counters search; the layout follows the width of the host (`data-narrow`/`data-compact`), not the window. Saves check that the item was not changed elsewhere since the editor opened (`itemSnapshot`). Tables are read-only, one line per row (long names truncate with the full text in a `title`); a row has an Enabled switch (saves on its own) and Edit / Duplicate / Remove icons. Editing is **draft-and-save**: the editor card holds a draft and nothing is written until Save (a discard dialog guards every exit). All config is stored through Splunk REST in `assetdb.conf`: the `[general]` stanza holds `lookups` (a JSON array of source objects: `name`, `lookup`, `enabled`, `role`, `scope`, `max_age`, `time_field`, `filter`, `columns`) and the global settings (`max_keys`, `max_key_share`, `key_blocklist`, `ignore_values`, `min_ratio`, `runs_to_keep`, `scope_field`, `default_*`, ...); every other stanza is a field (a field may also set `enabled=0` to be left out of the merge). A save is a chain, each step reported on its own: config writes, `syncCollection()` (KV indexes, field types, the `adb_enrich_outputs` macro), then regeneration of the saved search `assetdb-lookupgen`. Row counts, columns and unreadable lookups are read once per source with one-shot searches (`inspectLookup`) and drive the warning icons. Edit only `src/*.js`; `*.min.js` are committed build output. `tests/js/load-generator.js` evaluates the real `assetdb.js` in a vm sandbox and exports `searchText`/`searchLines`, so keep the file ending in `init();`.
3. **Explorer and Coverage dashboards** (classic Simple XML, `assetdb_explorer` and `assetdb_coverage`, generated by `scripts/build-dashboards.py`) and the **custom visualizations** in `viz/`. A dashboard defines its searches in the XML (`<search id=...>`); its script (`js/src/adb_explorer.js`, `adb_coverage.js`) puts the built visualization (`js/classic/<name>.min.js`) in an iframe through `adb_frame.js` (srcdoc iframe; the bundles live under `appserver/static/js/` because Splunk wraps every other script it serves from an app in `i18n_register(...)`, which a plain iframe page does not have), feeds it the search results (`json_cols`) and the theme by postMessage, and turns its drilldown messages into tokens (Explorer: `adb_q`, `adb_asset`) or, for Coverage, into a search opened in a new window (`buildCoverageDrillSearch` in `generator.js`). The visualizations are unchanged between the classic and the Studio build (Splunk 10.4+, `framework_type = studio_visualization`, not exported). They run in a sandboxed iframe and talk to their host only through the `VisualizationAPI` of `@splunk/dashboard-studio-extension` (or its classic stand-in). Pure logic (shape-based labels, matrix and asset parsing, provenance, palettes) is in `viz/shared/*.mjs` and unit tested in `tests/js/viz-models.test.js`. What Studio actually does, learned by probing a real 10.4.2: a multivalue field arrives as an array, the theme is `{theme: 'light'|'dark'}`, and a viz can reach the dashboard only through `triggerDrilldown`, of which the host forwards just `name`, `value` and keys starting with `row.` or `click.`. The explorer sends both `click.sel` and `click.q` on every event so the two tokens are always set together. **Explorer** (`adb_asset_explorer`): data source `primary` is the asset search (100 rows, `adb_total` carries the real count), `provenance` (optional) is `adb_provenance` for the selected asset; user fields are never named. **Heatmap** (`adb_heatmap`): first column labels rows, other columns are 0-100 series, `adb_total` (row size) and `<series>__n` (counts) are optional. **Themes**: Splunk Web themes a classic (Simple XML) page only from the dashboard's `theme` attribute or a `?theme=light|dark` parameter, never from the user's preference or `supported_themes` in `app.conf` (`get_dashboard_theme` in Splunk's `view.py`: URL, then XML, then the user theme only for apps in `supported_themes`, which that code fills only for the ES app). The three views therefore carry `theme="dark"` (dark is the default and paints dark from the first byte) and `adb_theme.js` reads the user's preference (`user-prefs`) and reloads the page once with `?theme=light` when it is `light` (anything else, including `default_system_theme`, stays dark); a URL that already has `?theme=` is left alone, which also previews a theme without saving anything. The last preference is cached in localStorage so later visits reload at once, the old page is covered with the new page's color during the reload, and each page script calls it in a `require` of its own so it does not wait for the page. About 0.4 s of the old theme before any app script runs cannot be avoided (Splunk's server HTML links only the light stylesheet and an app's css/js are added by script, and `dashboard.js` is requested at the same moment as the view script). The Configure SPA sets `data-theme` on its host (dark tokens in `assetdb.css`); the dashboards carry `theme="dark"`. `app.conf` still declares `supported_themes = light,dark` for Splunk's modern pages (no space: that is how Splunk's own apps write it). The run history and overflow list are plain KV collections to search.
4. **`adbmerge` custom command** (`bin/adbmerge.py` thin wrapper, `bin/adbmerge_core.py` pure logic, vendored `lib/splunklib` 3.x, Python 3.13): union-find merge of rows that share any key; enrich-only rows (`adb_auth=0`) attach to exactly one asset and never link; keys shared by more than `max_key_share` rows are skipped; clusters over `max_keys` (hard cap 100) are dropped or emitted for review (`overflow=emit`); counters are stamped on the output for the run record. The chunked protocol takes column names from the first record, hence `with_common_fields`.
5. **Storage** (`collections.conf`, `transforms.conf`): `assetdb` (merged assets), `assetdb_runs` (bounded run history), `assetdb_overflow` (last run's oversized clusters); each with a lookup definition.
6. **Macros** (`macros.conf`): `input_adb_lookup`, the `normalize_*` presets (multivalue safe, used by the generator), `adb_enrich*` (exported), `output_adb_lookup` and helpers. The **merge steps** that do not depend on the configuration are static macros the generated search calls (`adb_merge(max_keys, max_key_share)`, `adb_save_overflow`, `adb_run_guard(min_ratio)`, `adb_record_run(min_ratio, runs_to_keep)`, `adb_write_gate`, `adb_map_column(field, lookup, column)` (a source column into a field), `adb_tag_time(field)`, `adb_newest_first(field)`, `adb_key_blocklist(field)` / `adb_key_blocklist_cs(field)` (the default key blocklist; a customized `key_blocklist` is written out inline by `valueFilter`), `adb_counters`); the generator only passes arguments. `tests/js/macros.js` expands them so tests can assert on what the search does (`gen()` in `merge-search.test.js`), the goldens show the unexpanded search, and `buildPreviewDiff` knows which of them write (`adb_save_overflow`, `adb_record_run`) and drops them. Keep their definitions free of backslashes and of anything configured. `adb_provenance(1)` is **generated**: `generator.js` builds its definition (`buildProvenanceMacro` from the sources and fields); `syncCollection()` POSTs it on every save, like `adb_enrich_outputs`, and the Configure page also installs it on load when the installed one differs (`ensureProvenanceMacro`); `macros.conf` only holds the starting stub. `adb_icon` is **written by the user**: a plain eval in `macros.conf` (documented there, default `eval adb_icon="other"`) that must output one of `ICON_CHOICES`; the visualization falls back to `other`, so every asset has an icon; the Settings tab links to the macro editor; nothing generates it. The set of icons is fixed (`ICON_CHOICES`, which a test keeps equal to `viz/shared/icons.mjs`).
7. **Templates**: disabled `assetdb-src-*` saved searches in `default/savedsearches.conf` that build source lookups: five generic ones and one per vendor add-on (listed in the README). A vendor template reads field names taken from the add-on itself (props.conf aliases, lookups `fields_list`, input code, samples): when you change one, read the add-on again rather than guess. They write the vendor's own record ID next to the CIM names, never use an external (NAT) address, and read an add-on's own macro or eventtype for the index. `tests/integration/test_templates.py` runs each on sample events (the first pipe separates the data source from the transformation, which the test swaps for the events), `tests/python/test_templates.py` checks the conf statically. Splunkbase packages can be downloaded with the API (login `POST /api/account:login/`, then `/app/<id>/release/<version>/download/` with `X-Auth-Token`); credentials come from `SPLUNKBASE_USER`/`SPLUNKBASE_PASSWORD` in `.env.local` and the username is the splunk.com username, not the email.

`lookups/assetdb_demo_assets.csv` is the demo source lookup registered by default in `assetdb.conf`.

8. **Vendor logos** (`assets/vendors.json` + `assets/vendors/`): `python3 scripts/build-vendor-icons.py` embeds the logos in `viz/shared/vendor-icons.mjs` (visualizations) and `appserver/static/js/src/vendor_icons.js` (Configure page). A source's logo is picked automatically from keywords in its name or lookup name (`vendorFor`; the order of the file is the priority, short keywords match whole words only). There is no setting. The Explorer and Coverage pages get the lookup names from the search `ds_sources` (reads `conf-assetdb/general`; if a role cannot, the name alone is used). `make test` fails when the generated files are stale. Logo sources and brand notes: `assets/README.md`.

## Gotchas

- `input_adb_lookup` sets `adb_src` (an internal marker) and `source_lookup` from it, so a `source_lookup` column inside a source lookup (a copy of a merged result) is ignored. `inputlookup append=true` chains all lookups in one pipeline, which is why the marker is set only where it is null.
- In `stats`, single-quoted field names (`values('ip{}')`) are not field names: `rename "ip{}" as ip` first. `eval` accepts the single quotes.
- `adb_provenance` is generated; it calls the shared macros `adb_prov_match` and `adb_prov_end` (macros.conf). Quoted macro arguments lose their quotes (that is how lists with commas are passed); `$key$` is passed bare and quoted by the macro.
- The Explorer's "differs" compares each source with the newest one and with the final value of the asset (`viz/shared/provenance.mjs`); never only with the final value, which the merge has normalized.
- The repo lives in iCloud Drive, which evicts and duplicates files: `node_modules` is a symlink to `node_modules.nosync` (iCloud skips `.nosync`), and stray `name 2.ext` copies are git-ignored and excluded from the package (the archive check fails if one gets in). If a build suddenly fails with a missing module, run `npm ci`.

- `python.required = 3.13` and splunk-sdk 3.x mean `adbmerge` needs a Splunk whose custom commands run on Python 3.13 (10.4.2 is tested; 10.0 always uses its bundled Python 3.9).
- `npm install`/`npm ci` also remove a Playwright installed with `--no-save`; reinstall a version whose browser is cached (`npm i --no-save playwright@1.64.0`).
- Large data: `eventstats` and `join`-like steps keep events in memory and truncate silently past `max_mem_usage_mb` (200 MB); use `stats` (it spills to disk) for anything that sees all the rows (`adb_merge` does). Measure on a 500,000 row lookup before changing a search: a `where` in `inputlookup` or `inputlookup append=t` looked like wins and were not (see CHANGELOG, Performance). `sort N` beats `sort 0 | head N`; `eventstats count` over all assets costs more than the rest of the Explorer search.
- Splunk removes the quotes around a quoted macro argument (`adb_x("a b")` gives the macro `a b`), so a macro that needs a string must add the quotes itself (`adb_provenance` does: `_key="$key$"`) and callers pass the value bare. `tests/js/macros.js` does the same when it expands macros.
- Field names `_key`, `asset`, `source`, `source_lookup`, `last_seen`, `scope`, `conflicts` are reserved (created by the merge).
- Booleans in `assetdb.conf` are `0`/`1` strings; lists (`ignore_values`, `key_blocklist`) are JSON strings; the generator parses them with fallbacks.
- Splunk Web caches app static files per build: after a deploy restart splunkd (`/_bump` is refused on Splunk Free) and hard-refresh.
- Integration/e2e tests need `.env.local` and write only to temporary objects (`adbtest_*`); the e2e flow edits the real config and restores it. If a flow run is interrupted, remove a leftover `adbtest_*` field by hand and check the saved search is `| makeresults` again.
